# E2E-S2.2C — Yahoo symbol candidate resolver

Status: implemented offline subcomponent; S2.2C remains open.

## Boundary

`YahooSymbolResolver.resolve` accepts `MarketListing` or `ListingKey`.
It preserves `(exchange, symbol)` and produces `SymbolMappingResult`.
It does not import yfinance, contact the network, apply eligibility, mutate
source records, require ISIN, choose another venue, or verify identity.
Callers enforce Scanner eligibility separately; portfolio callers can reuse
mapping without filtering their existing holdings.

RESOLVED means exactly one syntactic candidate, not a verified instrument.
All suffix rules remain subject to downstream live identity and availability
checks. Unit tests establish deterministic transformations, not Yahoo coverage.

This is a candidate-rule registry, not a change to production exchange coverage.
Generic US acquisition scope is not a listing venue. No generic US or foreign
venue fallback exists. Unsupported venues stay UNMAPPED.

Plain alphanumeric symbols and internal hyphens are preserved. US `.A` and `.B`
share-class endings become `-A` and `-B`. For ST and CO only, a dot or one space
before terminal A/B becomes a hyphen. Other punctuation requires an override;
the resolver does not strip existing suffixes or infer London special cases.

The Yahoo [VOLV-B.ST quote page](https://finance.yahoo.com/quote/VOLV-B.ST/)
provides an example of the target class representation. This is not evidence
that every input generated by these rules is a valid Yahoo instrument.

## Overrides and versioning

`YahooSymbolOverride` requires an exact ListingKey, candidate tuple, reference,
and reason. One candidate resolves; multiple distinct candidates remain
AMBIGUOUS; an empty tuple explicitly blocks the mapping. No built-in overrides
are shipped. Venue suffix consistency is checked; unsupported venues require
a new ruleset before overrides can be configured. Such checks do not replace
live identity verification, particularly for unsuffixed US listings.

Duplicate override keys and malformed configurations raise ValueError.
Wrong Python input types raise TypeError; no fabricated listing key is used
to construct INVALID_INPUT. Unsupported ticker syntax yields UNMAPPED with a
diagnostic. The INVALID_INPUT enum remains available to future input boundaries.

The mapping version combines a ruleset version and a SHA-256 digest of the
complete sorted override content. Changes to candidates, reasons or references
invalidate downstream verification keys. Future changes to rules must bump
YAHOO_RULESET_VERSION.

## Batch semantics

`resolve_many` sorts and deduplicates exact listing keys. Distinct keys sharing
one resolved Yahoo symbol all become UNMAPPED with YAHOO_SYMBOL_COLLISION.
The proposed symbol and involved keys remain in the diagnostic. AMBIGUOUS is
reserved for multiple candidates for one key, consistent with the contract.
Collisions are detected only within the supplied batch; callers should map
the complete input universe before dividing verification into network batches.
No cross-venue or ISIN deduplication occurs.

## Offline audit

`python -m tools.audit_scanner_yahoo_mapping --input-report <S2.2B-report.json>`
reads the prior eligibility report and maps only ELIGIBLE records. It validates
counts and duplicate keys, writes a new report under data/cache/scanner, and
makes no network calls, including no exchange discovery. Its SUCCESS means
the audit completed, not that all candidates resolved or have market data.
